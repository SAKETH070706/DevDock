# DevDock Audit — For ACE Chat Planning

No code was changed. This is a read-only inspection of `devdock/serverSide` and `devdock/clientSide`.

---

## 1. Project Structure

**Backend** (`serverSide/src`, Express 5 + Socket.IO 4 + Mongoose + ioredis):
- `server.js` — app bootstrap, HTTP server, Socket.IO server creation, socket auth middleware
- `socket/socketHandler.js` — **all** chat/room/editor socket event handlers live in this one file
- `models/roomModel.js`, `models/userModel.js` — the only two Mongoose models in the project
- `controllers/roomController.js`, `controllers/disbandRoomController.js` — REST room endpoints
- `services/roomService.js` — room create/join/leave/disband business logic
- `middleware/authMiddleware.js` — REST JWT auth (separate from socket auth)
- `services/authService.js`, `controllers/authController.js` — registration (OTP-gated), login, password reset
- `utils/generateRoomCode.js` — 6-char alphanumeric invite code generator
- `config/redis.js` — ioredis client, used for invite-code lookup and online-presence sets

**Frontend** (`clientSide/src`, React + Vite):
- `services/socket.js` — single shared `socket.io-client` instance (not auto-connecting)
- `hooks/useRoomSocket.js` — **all** chat/room socket wiring for the React app lives here
- `components/room/ChatSection.jsx` — dumb UI component (message list + input)
- `context/AuthContext.jsx` — stores JWT + user object in `localStorage`
- `pages/Room.jsx` — page that composes room data, socket hook, and room actions

There is no dedicated "chat" module — chat is one event handler inside the generic room socket handler, alongside collaborative-editor sync (Yjs), language sync, and presence.

## 2. WebSocket / Socket.IO Connection Flow

```
Frontend (services/socket.js)
  io(VITE_SOCKET_URL, { autoConnect: false })
      │
      │  useRoomSocket.js: on mount, reads JWT from localStorage,
      │  sets socket.auth = { token }, calls socket.connect()
      ▼
Backend (server.js)
  io.use(async (socket, next) => { ... })   ← Socket.IO middleware, runs before "connection"
      │  reads socket.handshake.auth.token
      │  jwt.verify(token, JWT_SECRET)
      │  User.findById(decoded.id)
      │  attaches socket.user = <full user doc>
      ▼
  io.on("connection", socket => { ... })     ← socketHandler.js
      │  socket is now authenticated; socket.user is trusted for the rest of its life
      ▼
  socket waits for a "join-room" event before joining any Socket.IO room
```

Key facts:
- One shared socket per browser tab, not one per room — room membership is layered on top via `socket.join(roomId)`.
- Auth happens **once**, at the transport-connection level, via a Socket.IO `io.use()` middleware — not per-event.
- A connected user is identified by `socket.user` (full Mongoose user document, attached during the auth middleware) and by `socket.data.roomId` / `socket.data.userId` (set after a successful `join-room`).
- If no token, invalid token, or user not found → `next(new Error(...))`, and Socket.IO rejects the connection before `"connection"` even fires. There is no path for an unauthenticated socket to reach any handler.

## 3. Room Creation and Joining

**Room ID vs invite code — these are two different things:**
- `room._id` — standard Mongo ObjectId, the permanent room identifier. Used for `socket.join(roomId)`, all REST room routes, and DB relations.
- `inviteCode` — a separate 6-char `[A-Z0-9]` code generated by `generateRoomCode.js` (`Math.random()`, not crypto-secure, not a UUID). Regenerated-on-collision via a `do...while` loop checking Redis. **Stored only in Redis** (`room:<inviteCode>` → roomId), with a **10-minute TTL** (`INVITE_CODE_EXPIRY = 10 * 60`). It is *not* persisted on the Room document in a queryable way beyond the `inviteCode` field being copied onto the Mongo doc at creation time (but that field isn't re-validated against Redis after expiry).

**Create flow** (`POST /api/rooms/create`, REST, JWT-authed):
`createRoom(roomName, language, hostId)` → generate unique invite code → `Room.create({ host, participants: [host], ... })` → `redis.setex(room:<code>, 600, roomId)`.

**Join flow** (`POST /api/rooms/join`, REST, JWT-authed):
`joinRoom(inviteCode, userId)` → `redis.get(room:<code>)` → if missing/expired, error "Invite code expired or invalid" → load Room by that id → check `isActive` → push `userId` into `participants` array if not already present → `room.save()`.

**Note:** joining a room (adding to `participants`) happens over REST, *before* any socket involvement. The socket layer only ever checks existing membership — it never adds anyone to `participants`.

**Socket-side room join** (`join-room` event, after REST join has already granted membership):
1. Validate `roomId` is a Mongo ObjectId.
2. `Room.findById(roomId)`, check `isActive`.
3. Check `socket.user._id` is `host` or in `participants` — **this is the only membership check for sockets**; if not a member, emits `"unauthorized"` and does not join.
4. `socket.join(roomId)` (native Socket.IO room), plus `socket.data.roomId`/`userId` set for later validation.
5. Add user to a Redis set `room:<roomId>:users` (presence tracking, separate from Mongo `participants`).
6. Broadcast `"participants-updated"` (tells clients to re-fetch room via REST) and `"online-users"` (the Redis set contents) to everyone in the Socket.IO room.

So: **Socket.IO rooms are used purely for broadcast fan-out**, keyed by Mongo `roomId` string. Actual membership authorization is backed by MongoDB (`participants` array); online presence is backed by Redis (ephemeral).

## 4. Chat Message Logic — Full Trace

```
User A types in ChatSection.jsx input, clicks Send
   → Room.jsx: handleSendMessage() → sendMessage(message) from useRoomSocket
   → useRoomSocket.js: socket.emit("chat-message", { roomId, message })
        (no client-side validation beyond message.trim() non-empty)
   ▼
Backend socketHandler.js: socket.on("chat-message", ({ roomId, message }) => { ... })
   → validate roomId is ObjectId
   → validate socket.data.roomId === roomId   (must have already joined this exact room)
   → validate message is a string, non-empty after trim, ≤ 1000 chars
   → message = message.trim()
   → io.to(roomId).emit("chat-message", {
         userId: socket.user._id,
         username: socket.user.username,
         message,
         timestamp: Date.now()
     })
        (broadcast to EVERYONE in the room, including the sender —
         there is no separate "echo to sender" vs "broadcast to others" split)
   ▼
User B's useRoomSocket.js: socket.on("chat-message", data => setMessages(prev => [...prev, data]))
   ▼
ChatSection.jsx renders msg.username + msg.message from local React state
```

- **Event name**: `"chat-message"` used both for client→server emit and server→client broadcast (same name, different direction).
- **Payload in**: `{ roomId, message }` (string).
- **Payload out**: `{ userId, username, message, timestamp }` — `userId`/`username` come from the authenticated `socket.user`, **never from client input** (good — can't spoof sender identity).
- **Timestamp**: server-generated `Date.now()` (ms since epoch), not persisted, not used for ordering beyond client array append order.
- **Error handling**: try/catch around the handler logs to console; invalid payloads are silently dropped (no error event emitted back to the sender for bad chat messages, unlike `join-room` which does emit `room-error`/`unauthorized`).
- **No read receipts, no message IDs, no edit/delete, no typing indicators.**

## 5. Message Persistence

**There is no message persistence anywhere.** No Mongo model for messages, no Redis storage of message content (Redis is only used for invite codes and the online-users presence set), no `localStorage` write for messages on the client.

Messages exist only in:
- Server: transient function-call scope inside the `chat-message` handler (never stored after the `io.to(roomId).emit(...)` call).
- Client: a React `useState` array (`messages`) inside `useRoomSocket`, scoped to the component's lifetime.

Concretely:
- **Page refresh** → `messages` state resets to `[]`; nothing is re-fetched from a server, because there is nothing to fetch. Chat history is gone.
- **User leaves and rejoins room** → same as above; empty message list on rejoin.
- **Server restart** → irrelevant, since messages were never server-stored either.
- **Room closes/disbands** → Room doc and Redis keys are deleted (see §6); no message data existed to lose.

This is the single biggest gap relative to ACE Chat's requirement ("messages need to be stored in MongoDB... available after refresh/reconnection").

## 6. Room Lifecycle

- **Room creator (host) disconnects** (socket drop, not explicit leave): only the `"disconnect"` handler runs — it removes the user from the Redis online-users set and re-broadcasts `"online-users"`. **The room itself is untouched**; `host` stays as-is on the Mongo doc; `isActive` stays `true`. There is no "host left, room over" logic tied to socket disconnect — only tied to the explicit REST `leave-room` flow (§ below).
- **Explicit "leave room"** (`POST /:roomId/leave`, REST — not a socket event despite the socket also having a `leave-room` event that only handles presence): `leaveRoom()` service removes the user from `participants`; if that user was `host`, host reassigns to `participants[0]` if others remain, else the room is marked `isActive: false` (soft-close, doc not deleted).
- **Another (non-host) user disconnects**: same as host case — presence-only cleanup, no membership change.
- **Everyone leaves** (via the REST leave flow): last leaver being host → `isActive = false`. The Room document is **not deleted**, just flagged inactive. Any socket still trying to `join-room` afterward is rejected (`room.isActive` check).
- **Server restarts**: Redis presence sets (`room:<id>:users`) and invite-code keys are lost unless Redis has its own persistence configured (docker-compose mounts a `data/redis` volume, so likely has AOF/RDB, but that's Redis-level, not app-level). Mongo `Room` docs (and `participants`) survive since MongoDB is durable. In-memory-only chat messages are gone regardless.
- **Explicit "disband room"** (`DELETE /:roomId`, host-only, REST): deletes the invite-code Redis key, deletes the `room:<id>:users` Redis key, and **hard-deletes the Mongo Room document**. The controller then does `io.to(roomId).emit("room-disbanded")` via `req.app.get("io")` (REST controller reaching into the Socket.IO instance to broadcast) so connected clients get kicked out.
- **Joining an invalid/expired room ID**: REST join checks Redis invite code first (10-min TTL — after expiry, "Invite code expired or invalid" even if the Mongo room still exists and is active). Socket-side `join-room` on a non-ObjectId or nonexistent/inactive room emits `"room-error"`; on a valid-but-not-a-member room, emits `"unauthorized"`.

## 7. Existing Authentication

- **Scheme**: JWT, `jsonwebtoken`, signed with `JWT_SECRET`, 30-day expiry (`generateToken` in `authService.js`).
- **Password storage**: bcrypt-hashed (`bcryptjs`, cost 10).
- **Registration**: multi-step — email/contact submitted → OTP emailed (via Resend or Brevo, `emailService.js`) → OTP verified → registration finalized → user created. Registration intermediate state is held in **Redis**, not Mongo (`otpService.js`: `storeRegistrationData`, `markEmailVerified`, etc.), so it's self-expiring if abandoned.
- **Token storage (client)**: `localStorage` (`AuthContext.jsx` — both `token` and the `user` object as JSON, not `httpOnly` cookies).
- **REST validation**: `authMiddleware.js` — reads `Authorization: Bearer <token>` header, `jwt.verify`, loads `User` by decoded id (password field excluded), attaches `req.user`. Applied per-route in `roomRoutes.js` (every room route is behind it).
- **Socket validation**: separate implementation, inline in `server.js` as an `io.use()` middleware (not reusing `authMiddleware.js` — duplicated logic, slightly different shape: reads `socket.handshake.auth.token` instead of a header, attaches `socket.user` as the full user doc rather than a password-stripped one... actually it also doesn't `.select("-password")`, so the password hash **is** present on `socket.user` server-side, though it's never sent to clients).
- **Does chat associate a socket with a logged-in user?** Yes, fully — `socket.user` is trusted server-side for every emitted message's `userId`/`username`. There's no anonymous or guest path.
- **No refresh tokens, no token revocation/blacklist, no role/permission field on `User` at all** — the schema is just `username`, `email`, `contact`, `password`. There is no concept of roles (admin/student/host beyond "room host") anywhere in the codebase.

## 8. Classification: Reusable vs Not for ACE Chat

### DIRECTLY REUSABLE (copy/adapt with minimal changes)
- The `io.use()` JWT-handshake-auth pattern for authenticating sockets before `"connection"`.
- The `socket.data.roomId` / `socket.data.userId` pattern for binding a connected socket to a validated room, then re-checking `socket.data.roomId === payload.roomId` on every subsequent event (cheap, effective anti-spoofing for "which room is this socket allowed to act in").
- Server-trusts-`socket.user`-not-client-payload pattern for `userId`/`username` on outgoing messages.
- `ObjectId.isValid()` guard-before-query pattern used throughout.
- The bcrypt + JWT auth stack (`authService.js`/`authMiddleware.js`) as a base, though ACE Chat's identity-verification requirement (linking to existing ACE registration) means registration itself needs new logic layered on top.
- General project shape: `routes → controllers → services → models`, and Socket.IO `io.use()` + a single handler-registration file.

### REUSABLE CONCEPT (architecture is right, implementation should differ)
- **Room/group membership model** — the host/participants pattern is a reasonable starting point for admin/student groups, but needs a role field (ACE Chat requires enforced admin-vs-student, not just "host vs participant").
- **Invite-code join flow** — the Redis-TTL invite code idea is fine conceptually for "join a group via code or link," but a 10-minute TTL is wrong for a long-lived student group (ACE Chat groups presumably persist indefinitely, not just for one live session) — this needs to become a durable, non-expiring (or admin-controlled) invite mechanism, likely stored on the Group document itself rather than only in Redis.
- **Redis online-presence set** — fine as a presence indicator, but not needed for ACE Chat's core requirement (message history matters more than live "who's online").
- **`socket.on("chat-message", ...)` broadcast pattern** — the shape (validate → build trusted payload → `io.to(room).emit`) is reusable, but it must add a **persist-to-MongoDB-before-broadcast** step, and it must add a **server-side role check** ("is this socket's user an admin/EBM of this group?") before allowing the emit to do anything — DevDock never asks "can this user send messages here," only "is this user in this room."
- **`room-disbanded` REST-controller-reaches-into-`io`** pattern (`req.app.get("io")`) — useful for admin actions (e.g., admin removing a student, admin closing a group) triggering realtime pushes from REST endpoints.

### NOT NEEDED
- Yjs collaborative code-editor sync (`yjs-update`, `awareness-update`, the whole `yjs/` folder) — DevDock-specific, irrelevant to a chat app.
- `language-change`/`language-update` (code-execution language sync) — compiler-specific.
- `saveCode`, `Execution` model, compiler/execution services and routes — code-execution feature, unrelated.
- History/execution-history feature (`historyController.js`, `historyService.js`) — tied to code execution, not chat.
- Host-reassignment-on-leave logic — ACE Chat groups have admins by role/authorization, not by "whoever created the room," so this specific mechanic doesn't map over.
- Ephemeral 10-minute invite codes as the *only* join mechanism — too short-lived for ACE Chat's use case.

## 9. What ACE Chat Needs vs What DevDock Already Solves

| ACE Chat requirement | DevDock status |
|---|---|
| Admins/EBMs send, students read-only | **Missing entirely.** No role concept anywhere in DevDock; every room member can emit `chat-message`. Needs a role field + server-side authorization check in the socket handler (and REST, if messages can also be sent via REST). |
| Groups/rooms | **Partially solved.** Room model + host/participants pattern is a usable starting skeleton, but needs role-aware membership (admin vs student) instead of host vs participant. |
| Join via group ID or invite link | **Partially solved.** Invite-code mechanism exists but is Redis-only and 10-minute TTL — needs to become durable (stored on the Group doc, no forced expiry, or admin-configurable). |
| Registered student's ACE ID linked to ACE Chat account, prevent identity theft of another student's ACE ID | **Not present.** DevDock's `registerUser` only checks email/contact uniqueness via OTP; there's no concept of matching against a pre-existing external record. This needs new logic: verify submitted registration details against the existing ACE registration collection (e.g., match on ACE ID + some second factor already on file — email/phone from registration — before allowing account creation), and mark the ACE ID as claimed so it can't be reused for a second account. Nothing in DevDock does identity verification against a separate pre-existing dataset; this is fully new logic. |
| Messages stored in MongoDB, available after refresh/reconnect | **Missing.** No Message model, no persistence step in the socket handler. Needs a new `Message` model and a "save then broadcast" (or "save then fetch-on-join") flow. |
| Real-time delivery via Socket.IO | **Solved, pattern reusable.** The auth-then-join-then-emit pipeline is a good base. |
| Mobile-friendly, eventually PWA | **Not addressed by backend/socket layer at all** — this is a frontend concern; DevDock's `ChatSection.jsx` is a bare unstyled placeholder, not mobile-considered. Nothing to reuse here; frontend needs to be built fresh with PWA in mind (manifest, service worker, responsive layout). |
| Only authorized admins can send | Same gap as role requirement above — needs explicit server-side check, e.g. `GroupMember.role === "admin"` (or similar), verified from the DB, never trusted from the client, before accepting a `send-message` event. |
| Students see history of groups they belong to | **Missing** — depends on the new Message model + a "fetch messages for group I'm a member of" REST or socket flow, which doesn't exist in any form today (DevDock has no analogous "fetch chat history" endpoint — `historyController.js` is about code-execution history, not chat). |

## 10. Database Design Impact

DevDock's two models (`User`, `Room`) are too thin for ACE Chat's requirements — particularly because DevDock embeds `participants` as a raw array on `Room` with no per-member metadata (no join date, no role), and has no Message model at all.

Likely ACE Chat collections (naming is illustrative, not prescriptive):

- **User / Account** — the ACE Chat login identity. Needs a link field to the existing ACE registration record (e.g., `aceId` or a reference to the ACE registration document) plus whatever is used to verify that link (see §9) so one ACE ID can't be claimed by two accounts (unique index on that link field solves the "steal someone else's ACE ID" problem at the DB level, in addition to the verification-at-registration-time check).
- **ACE Registration** (likely already exists per your note — "ACE registration data already exists in MongoDB") — treated as read-only source-of-truth to verify against, not owned by ACE Chat.
- **Group** — replaces DevDock's `Room`. Needs: name, invite code (durable, not TTL'd), and likely an explicit `admins`/`createdBy` field. Given the role requirement, **don't** reuse DevDock's flat `participants: [ObjectId]` array as the only membership structure — a separate join model (below) is cleaner once you need per-member role and per-member metadata (joinedAt, etc.).
- **GroupMember** (join table between User and Group) — `{ group, user, role: "admin" | "student", joinedAt }`. This is where "can this user send in this group" gets checked server-side. DevDock has no equivalent — its host/participants split is a much weaker version of this idea (role is implicit in "are you the one host" rather than a real field).
- **Message** — `{ group, sender (User ref), content, createdAt }` at minimum, likely `{ readBy: [User] }` or similar later if read-receipts matter. This has **zero equivalent in DevDock today** — the entire persistence layer for chat needs to be built new.

Relationships: `User —< GroupMember >— Group`, `Group —< Message >— User(sender)`. This is a standard many-to-many-with-role shape; DevDock's current `Room.participants` array is a simpler (host-implicit-role) version of the same idea and can inform the Group/GroupMember split but shouldn't be copied verbatim given the explicit role requirement.

## 11. Security Weaknesses in the Existing Chat Implementation (relevant if adapted as-is)

- **Can a client fake a room ID?** No for join (validated against Mongo + membership check) and no for chat-message (`socket.data.roomId !== roomId` guard blocks acting in a room the socket hasn't actually joined). This part is solid and worth keeping.
- **Can a client emit a message event directly** (bypassing any UI)? **Yes, trivially** — any authenticated socket that has joined a room can emit `chat-message` directly with devtools/a raw socket.io-client script; there is nothing that ties message-sending to having gone through any particular UI flow. This is expected/normal for Socket.IO apps, but it means **all authorization must happen in the event handler itself**, which is exactly where ACE Chat's admin-only-send check needs to live (and where DevDock currently has *no* equivalent check for anything, since anyone in the room can chat).
- **Can an unauthenticated socket join?** No — the `io.use()` handshake middleware blocks the connection entirely before any handler runs. Solid, reusable.
- **Can a normal student send an admin-only event?** Not applicable to DevDock (no roles exist), but by direct analogy: DevDock's one place that *does* check a permission (`language-change` → "Only host can change language") shows the right pattern to replicate — re-fetch the authorization-relevant field from MongoDB inside the handler (`Room.findById(roomId).select("host")`) and compare against `socket.user._id`, rather than trusting anything the client claims about its own role. **This is the pattern ACE Chat's admin-send-check must follow** — a `role` field must be read from the DB (`GroupMember`) inside the `send-message` handler, never taken from the client payload or from a client-cached value.
- **Does the server trust role/identity information sent by the frontend?** No, for identity (`userId`/`username` always come from `socket.user`, never client payload) — this is done correctly and should be preserved. There's no role concept yet to evaluate, but the identity-trust pattern is the right template.
- **Is authorization actually enforced on the backend for the actions that matter?** Partially — room-membership is enforced for join/chat, but there is no message-send permission check at all (because DevDock treats all room members as equal chat participants). This is the core gap ACE Chat must close: right now *nothing* in this codebase distinguishes "can read" from "can send," so that logic is 100% new, not adapted.
- **Other notes**: `socket.user` server-side includes the bcrypt password hash (no `.select("-password")` in the socket auth middleware, unlike the REST `authMiddleware.js`) — never sent to clients today, but worth fixing if this code is reused, so a future bug (e.g., an accidental `socket.emit("profile", socket.user)`) can't leak hashes. Also, invite codes are generated with `Math.random()`, not a CSPRNG — low risk for a 10-minute-lived code, but worth using `crypto.randomInt`/UUID-style generation if ACE Chat's invite codes become long-lived/durable (longer lifetime = more time for brute-force guessing of a 6-char code).

## 12. Final Summary

**A. Existing DevDock chat architecture** — One shared client-side socket per tab; single server-side `socketHandler.js` registers all room/chat/editor events; Socket.IO rooms keyed by Mongo `roomId`; Redis used only for invite-code lookup (10-min TTL) and ephemeral online-presence sets; no chat-specific backend module — chat is one event among several (editor sync, language sync, presence) in one generic room handler.

**B. Existing socket events** — `join-room`, `leave-room`, `chat-message` (bidirectional name), `yjs-update`, `awareness-update`, `language-change` → `language-update`, `room-disbanded` (server→client only, triggered from a REST controller), plus built-in `connect`/`disconnect`. Error/status events: `room-error`, `unauthorized`, `participants-updated`, `online-users`.

**C. Existing room-ID generation logic** — Mongo ObjectId is the real room ID. A separate 6-character `[A-Z0-9]` invite code (`Math.random()`-based, collision-checked against Redis) is generated at room creation and stored in Redis with a 10-minute TTL, mapping code → roomId.

**D. Existing room lifecycle** — Created via REST (host + invite code). Joined via REST (invite code → membership added to Mongo `participants`). Socket `join-room` only validates pre-existing membership and manages presence/broadcast. Explicit REST leave reassigns host or soft-closes (`isActive: false`) the room. Explicit REST disband hard-deletes the Mongo doc and Redis keys, and broadcasts `room-disbanded`. Plain socket disconnect only affects presence, not the room record.

**E. Existing message flow** — Client emits `chat-message` with `{ roomId, message }` → server validates room-binding and content → server builds a trusted payload from `socket.user` → broadcasts to the whole Socket.IO room (including sender) → clients append to local React state. **No persistence at any point.**

**F. Existing authentication/socket authentication** — JWT (30-day expiry) issued at login after OTP-gated registration; REST routes protected by `authMiddleware.js` (Bearer header); sockets protected by a separate, duplicated `io.use()` JWT-handshake check in `server.js`. Both attach a trusted server-side user object. No roles/permissions field exists on the User model at all today.

**G. What is reusable for ACE Chat** — the socket handshake-auth pattern; the `socket.data.roomId` room-binding-and-recheck pattern; the "trust `socket.user`, never trust client-claimed identity" pattern; the REST-controller-triggers-`io.emit` pattern for admin actions; the overall routes/controllers/services/models project shape.

**H. What needs to be newly implemented** — role field + enforcement (admin/student, checked server-side from the DB inside the send handler, mirroring the existing `language-change`/host-check pattern); a durable (non-10-minute) group invite mechanism; a Message model and persist-before-broadcast flow; a fetch-group-history endpoint/event; the ACE-ID-to-account identity verification and anti-duplication logic (entirely new — nothing in DevDock resembles this); mobile/PWA-considered frontend (DevDock's chat UI is a bare, non-mobile-styled placeholder).

**I. Recommended ACE Chat architecture (high-level, for your review before implementation)** — Keep the shape of `io.use()` handshake auth + a `socket.data`-bound room join, but: (1) add a `GroupMember` collection carrying `role`, checked fresh from the DB on every send attempt, never cached client-side; (2) add a `Message` model, and change the send handler to `Message.create(...)` **before** `io.to(group).emit(...)`, so persistence never depends on a client staying connected; (3) on `join-group`, after validating membership, fetch and emit recent message history from MongoDB (paginated) instead of relying on any live-only state; (4) make invite codes durable, stored on the Group document itself (with an optional admin-triggered rotation/expiry, not an automatic 10-minute one); (5) build the ACE-ID verification as a distinct pre-registration step (verify submitted details against the existing ACE registration collection, then mark that ACE ID as claimed with a unique index) before any DevDock-style OTP/JWT registration logic runs.

**J. DevDock files worth studying/reusing concepts from**
- `serverSide/src/server.js` (socket handshake-auth middleware pattern)
- `serverSide/src/socket/socketHandler.js` (event-validation and room-binding pattern, especially the `language-change` host-check as a template for role checks)
- `serverSide/src/middleware/authMiddleware.js` + `services/authService.js` (JWT/bcrypt base, to extend — not copy — for ACE ID linking)
- `serverSide/src/services/roomService.js` + `models/roomModel.js` + `utils/generateRoomCode.js` (group/invite-code starting skeleton, needs role-awareness and durability changes)
- `clientSide/src/services/socket.js` + `hooks/useRoomSocket.js` (client-side connect/join/listen pattern)
- `serverSide/src/controllers/disbandRoomController.js` (REST-triggers-socket-broadcast pattern, useful for admin actions)

**K. Files not relevant to ACE Chat (skip)**
- Everything under `clientSide/src/yjs/`
